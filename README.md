# Еда

Помощник по питанию для телефона. Открыть — за пять секунд увидеть день целиком: что уже
съедено, что в плане на каждый из четырёх приёмов и сколько до цели по калориям и белку.
Выбрать приём — увидеть, что в нём лежит, что досыпать и в каком количестве, и одним
нажатием записать КБЖУ в дневник.

## Экраны

Приложение открывается на **сводке дня** (`src/ui/DaySummary.tsx`) — это первый экран,
а не текущий приём: прогресс дня (калории до цели, полоса из четырёх сегментов, белок,
ссылка «выгрузить день»), карточка на каждый из четырёх приёмов (название блюда, окно
времени, строка статуса — не записан / съел / съел часть / пропустил, пометка «сейчас» у
текущего по времени) и ниже — «Добавлено» (перенесённая еда и своя еда) и микронутриенты
за день.

У приёма, который ещё не записан, в карточке есть кнопка **«Съел»** — она пишет весь приём
целиком одним нажатием, не открывая экран приёма: для «поел по плану, отмечать нечего»
не нужно никуда заходить. Подробности приёма, доля («съел часть»), состав по спискам
«уже в контейнере» / «досыпать из пакетика», сборка и оценка блюда — только на экране
самого приёма, который открывается нажатием на карточку.

Под шапкой — навигация из пяти кнопок: «Сводка» и четыре приёма (`src/ui/SlotSwitch.tsx`).
На телефоне это горизонтальная полоса; на широком экране (от 48rem) она становится
боковой колонкой слева, и у каждого приёма в ней видна короткая строка статуса. Шапка
(дата, день цикла и партии, три иконки шторок) общая для обоих экранов —
`src/ui/ScreenHeader.tsx`.

Приложение ставится на телефон как обычное (PWA) и работает без интернета: меню и
справочник продуктов вкомпилированы в сборку. Сервера нет, аккаунтов нет, регистрации нет.

## Откуда берутся числа

Единственный источник КБЖУ и микронутриентов — **USDA FoodData Central, набор SR Legacy,
релиз 2018-04**. Ничего не вписывается руками и ничего не берётся «из головы».

`data/products.yaml` собирается скриптом `scripts/build-products.mjs` из офлайн-выгрузки
этого набора в CSV. У каждого продукта записан `fdcId` и дословное описание записи USDA,
по которым любое число можно проверить. Файл руками не правится: правка — это правка
скрипта и повторная сборка.

Две честные оговорки, обе видны в самом файле:

* **Творога в SR Legacy нет.** Взят `Cheese, cottage, lowfat, 2% milkfat` (fdcId 172182),
  это помечено полем `substitute`.
* **Столовая ложка чиа** в датасете не описана, взята общепринятая мера 12 г — помечено
  `tbspSource: common`. Все остальные меры (штука яйца и бразильского ореха, ложка льна
  и масла) взяты из `food_portion.csv` того же датасета.

Отдельное правило, важное для честности сумм: **отсутствие нутриента — это не ноль.**
Если в датасете для продукта нет строки по витамину K, поля `vitK` у него просто нет.
Ноль пишется только там, где в датасете реально записан ноль.

Верхний уровень файла несёт `revision` — дату (ГГГГ-ММ-ДД) последней правки СОДЕРЖИМОГО
справочника. Ставит её сам `build-products.mjs`, сравнивая новое тело файла со старым
(без строки `revision`): дата двигается, только когда тело реально изменилось, иначе
пересборка без единой правки числа не сдвигала бы её «задним числом наоборот». На
`revision` опирается снапшот записи дневника (`MealLogEntry.productsRevision`) — справочник
иногда правится задним числом (смена `fdcId`, новые нутриенты продукта), и без метки
нельзя понять, по каким числам посчитан день, уже отмеченный в дневнике.

## Меню

`data/menu.yaml` — восемь дней цикла по четыре приёма, собранные в **редакции**:
каждая редакция — одна порция меню, присланная диетологом, с необязательной датой
`from`, с какой она действует. Первая редакция может быть без `from` (действует
с самого начала) и обязана описывать весь цикл; следующие обязаны иметь `from`,
идти по возрастанию даты и вправе описывать только часть дней. Присланное не
переписывает прежнее — старая неделя остаётся в файле рядом с новой, потому что
человек по ней уже ел, и меню на конкретный день определяется правилом «самая
свежая из действующих на эту дату редакций, которая этот день описывает»
(`menuDayFor` в `src/core/menu.ts` — единственное место, где это правило живёт).
Это обычный текстовый файл, он правится руками, в коде меню нет нигде.

Каждая позиция несёт продукт, ровно одно количество (`g`, `pieces` или `tbsp`) и поле
`where`:

* `container` — уже лежит в контейнере готовым;
* `packet` — Александр досыпает или поливает сам перед едой.

На экране это два раздельных списка, и они не смешиваются.

## Проверка меню

```bash
npm run check-menu
```

Печатает каждую редакцию меню отдельно, своей шапкой — «РЕДАКЦИЯ: имя (действует
с датой); дней: N из 8» — с калориями каждого приёма, итогом дня, Б/Ж/У и попаданием
в коридор. День 4 есть в каждой присланной неделе, и сваливать редакции в одну
корзину значило бы приписать нарушения новой недели прежней.

Нарушения редакции делятся на два списка: «Так устроена вся редакция» — правило
сработало больше чем в половине её дней, это не опечатка, а другой замысел
диетолога, печатается одной строкой со счётчиком дней и примером — и «Выбивается
из редакции — проверить» — кандидаты в опечатку, печатаются поимённо (функция
`printViolations` в `scripts/check-menu.ts`). Итоговый счётчик считает все нарушения,
ничего не прячется. Смысл команды в том, чтобы ловить поломку **до того, как повар
закупится**.

Коды возврата различают два разных класса беды:

* **Файл сломан** (ссылка на несуществующий продукт, кривой YAML, отсутствующая мера) —
  выход 1 всегда, в том числе с флагом `--warn-only`. Такое меню нельзя показывать.
* **Питание не сходится** (день вне коридора, приём легче минимума, нет льна, ягоды
  дважды) — выход 1 без флага и выход 0 с `--warn-only`.

Флаг `--warn-only` стоит в непрерывной сборке. Логика простая: меню, которое на восемьдесят
калорий легче нормы, не должно снимать работающее приложение с телефона, а меню со ссылкой
на несуществующий продукт — должно.

Пороги живут в одном месте — `LIMITS` в `src/core/rules.ts`.

## Дневник и выгрузка

Записанный приём хранит **снапшот** своего КБЖУ. Правка меню задним числом не переписывает
уже записанные дни — иначе дневник врал бы о прошлом.

Выгрузка сделана каналами за общим интерфейсом (`src/core/export/types.ts`), и у контракта
одно жёсткое требование: **кнопка не имеет права делать вид, что отправила**. Канал либо
работает, либо честно объясняет, почему недоступен. Канал, который не может подтвердить
доставку сам, возвращает `pending` и говорит, чем подтверждение придёт.

Выгрузка открывается с двух мест: кнопка «Выгрузить» под записанным приёмом отдаёт этот
приём, ссылка «выгрузить день» у дневного итога — весь день сразу. Ссылки нет, пока за
сегодня ничего не записано: выгружать нечего.

Каналов три:

1. **Крупные числа и буфер обмена** — работает всегда, даже если всё остальное умрёт.
2. **CSV за день** — то же самое, но файлом; таблица `date,slot,title,kcal,…` с колонкой
   на каждый нутриент. Пустая ячейка означает «нет данных», `0` — измеренный ноль, а
   колонка `incomplete` перечисляет нутриенты, известные не по всем позициям приёма.
   Если системный шаринг файла недоступен, CSV показывается текстом для копирования —
   это предусмотренный путь, а не сбой.
3. **Apple Health через «Команды»** — основной путь, настраивается один раз.

## Apple Health: как собрать команду

Прямого пути из браузера в Health нет и быть не может — Health доступен только нативным
приложениям. Мост — приложение «Команды»: «Еда» открывает команду по ссылке и передаёт ей
словарь со всеми числами разом; команда кладёт их в Health и возвращает обратно.

Записать несколько показателей одним действием нельзя: в действии «Записать образец
здоровья» тип показателя задан жёстко и переменной не становится. Сколько показателей —
столько действий. Это ограничение Apple; родной трекер питания ожидается не раньше iOS 27.

**Приложение всегда отдаёт весь словарь целиком.** Сколько показателей реально ляжет
в Health — решает число действий в команде, а не приложение. Можно собрать команду на семь
показателей за пять минут и дособрать остальные когда угодно, ничего не меняя в приложении.

### Порядок сборки

1. Открыть «Команды», создать новую.
2. Переименовать её — это имя понадобится в настройках «Еды», оно должно совпадать
   буква в букву.
3. Первым действием добавить **«Получить словарь из ввода»** — оно разберёт то, что
   пришло из «Еды».
4. Дальше — по одному действию **«Записать образец здоровья»** на каждый показатель,
   который нужен. В каждом действии: выбрать тип из таблицы ниже, **проверить единицу
   измерения**, в поле значения подставить переменную словаря с соответствующим ключом,
   в поле даты — ключ `date`.
5. Сохранить. При первом запуске система один раз спросит разрешение на запись в Health.
6. В настройках «Еды» вписать имя команды. Пока поле пусто, канал Health выключен и
   честно говорит об этом.

## Перенос блюда между днями

Кнопка «Добавить блюдо из другого дня» на главном экране открывает шторку
`AddFromMenuSheet.tsx`: выбирается день цикла, приём, доля и дата записи (по умолчанию
сегодня), и блюдо этого приёма ложится в выбранный день как **добавленная еда** — отдельная запись, которая не трогает
статус собственного приёма текущего дня. Такие записи (`ExtraLogEntry`, ядро —
`addExtra`/`removeExtra` в `src/core/log.ts`) живут списком «Добавлено» под прогрессом
дня, каждая со своей долей, и несут самодостаточный снапшот КБЖУ и нутриентов — так же,
как обычная запись приёма.

## Своя еда через домашний компьютер

Кнопка «Своя еда» открывает шторку `CustomFoodSheet.tsx`: там книга уже разобранной
еды, форма нового заказа на разбор и очередь заказов с честными текстами состояния —
дословно теми, что показывает сама шторка (в очереди / ПК не в сети / разбор не удался /
запрос протух за сутки / готово).

Схема пути запроса: приложение → воркер Штурмана (`SHTURMAN_BASE` в
`src/core/foodClient.ts`, `https://shturman.vault-78edd5.workers.dev`, тот же воркер,
что и у sat-srs) → раннер на домашнем ПК → Claude Code с единственным инструментом
`food-search` → детерминированный `scripts/resolve-food.mjs` по данным USDA SR Legacy
2018-04.

На воркер уезжают только текст блюда, граммы и uuid запроса. Не уезжают: дневник,
настройки, токен — токен живёт исключительно в localStorage браузера и вводится в
Настройках (`SettingsSheet.tsx`, поле `Settings.shturmanToken`), в репозиторий он не
попадает никаким путём.

Числа считает не модель: она только подбирает записи USDA и граммы, а расчёт
КБЖУ и нутриентов из `per100` каждого компонента — детерминированная арифметика
приложения (`customFoodTotals` в `src/core/food.ts`, та же функция, что и у позиций
меню). Поэтому граммы компонента правятся локально (`withComponentGrams`), а смена
состава требует нового запроса на разбор.

Добавленная своя еда — тоже `ExtraLogEntry`, не меняет статус приёма и хранит
самодостаточный снапшот; книга разобранной еды (`AppState.customFoods`) отдельна от
уже записанных extras — удаление еды из книги на них не влияет.

## Что и где хранится

Всё состояние — настройки и дневник — лежит **только в localStorage браузера на самом
устройстве**. Никуда не отправляется, ни на какой сервер не попадает, ни с чем не
синхронизируется (кроме явной отправки текста и граммов своей еды на воркер по нажатию
кнопки — см. «Своя еда через домашний компьютер»). Очистка данных сайта стирает дневник.

Что именно хранится: дата первого дня цикла, ручной сдвиг цикла, цель по калориям,
имя команды Shortcuts, токен приложения для Штурмана, записи дневника по дням (включая
добавленную еду), книга своей еды (`customFoods`) и очередь заказов на разбор
(`foodRequests`).

Полный день (четыре приёма со снапшотом всех нутриентов) занимает около 7,4 КБ, а
localStorage в Safari ограничен примерно 5 МБ на сайт — это порядка 675 дней записей.
Поэтому настройки показывают размер дневника и дают стереть его целиком (`clearLog`),
а неудавшаяся запись не проглатывается: `saveState` возвращает причину, и экран
показывает её красной полосой. Автоматической чистки старых дней нет намеренно —
удалять записи молча приложение не должно.

Если при чтении хранилища что-то теряется — текст вообще не разобрался (повреждён)
либо часть записей не пережила проверку при загрузке, — дословная копия исходного текста
откладывается под отдельным ключом `eda.state.v1.backup`, до того как автосохранение
перепишет основной ключ уже почищенным состоянием. Экран сообщает об этом красной полосой
с кнопкой «Понятно» и называет ключ прямо в тексте — копию можно найти и разобрать руками
через инструменты разработчика браузера.

**Ключей, токенов и паролей в репозитории нет.** Разбор своей еды ходит к воркеру
Штурмана с токеном приложения, но сам токен в коде и в репозитории не хранится нигде —
его вводит человек в Настройках, и живёт он только в localStorage браузера.

## Разработка

```bash
npm install
npm run dev
```

| Команда | Что делает |
| --- | --- |
| `npm test` | Все проверки ядра, дневника, хранилища и выгрузки |
| `npm run test:menu` | Проверки разбора редакций и выбора действующего дня меню |
| `npm run test:food-resolve` | Проверки расчёта `resolveSpec` (`scripts/lib/usda.mjs`) по мини-фикстуре `test/fixtures/fdc-mini` — настоящие строки выгрузки, сама выгрузка не нужна |
| `npm run test:food` | Проверки домена «своя еда» — разбор ответа воркера, переходы очереди заказов, клиент `foodClient.ts` |
| `npm run check-menu` | Отчёт по меню и поиск нарушений |
| `npm run products` | Пересборка справочника из выгрузки USDA |
| `npm run food-search` | Поиск строк USDA по запросу (`scripts/food-search.mjs "<запрос>"`) — тот же инструмент, что вызывает модель на домашнем ПК при разборе своей еды |
| `npm run shots` | Снимки экранов настоящим headless-Chrome при поднятом `npm run dev`: первый запуск, день цикла, панель нутриентов с полосами, все шторки; код возврата 1, если полоса с процентом получила нулевую ширину. Путь к Chrome — переменная `CHROME` |
| `npm run icons` | Пересборка иконок приложения |
| `npm run build` | Сборка |

Пересборка справочника требует распакованной выгрузки SR Legacy:

```bash
npm run products -- "<путь к FoodData_Central_sr_legacy_food_csv_2018-04>"
```

Та же выгрузка нужна `food-search` и `resolve-food.mjs` (тесты `test:food-resolve` обходятся мини-фикстурой):
