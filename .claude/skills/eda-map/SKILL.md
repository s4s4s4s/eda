# eda — карта

React 19 + TypeScript + Vite 7, PWA (`vite-plugin-pwa`, `registerType: 'prompt'` — новая
версия скачивается сама, но подменяет экран только по нажатию человека). Открыть телефон,
за пять секунд увидеть текущий приём, что в нём лежит и что досыпать, и одним нажатием
записать его в дневник. Живёт на `s4s4s4s.github.io/eda`, деплой — GitHub Actions
(`.github/workflows/deploy.yml`, ветка `main`).

## Главное правило проекта

**Меню и КБЖУ — данные, а не код.** Хардкод меню в исходниках запрещён. Числа берутся
из одного заявленного источника (USDA FoodData Central, SR Legacy 2018-04) и у каждого
продукта записан `fdcId`. **Отсутствие нутриента в датасете — это не ноль:** поля просто
нет, а сумма несёт свою полноту (`known`/`total`), чтобы «неизвестно» никогда не читалось
как «измеренный ноль».

## Данные — `data/`

| Файл | Что внутри |
|---|---|
| `products.yaml` | справочник продуктов, 59 позиций: `per100g`, `micro100g` (все ключи `NUTRIENT_KEYS`), `tags`, меры `pieceG`/`tbspG` с полем `*Source`. Верхний уровень несёт `revision` (дата ГГГГ-ММ-ДД последней правки СОДЕРЖИМОГО, поле данных — см. `parseProductsRevision`); скрипт двигает её только когда тело файла реально изменилось, не при каждой пересборке. Собирается скриптом, правится редко |
| `menu.yaml` | `cycleDays` + список **редакций** (`editions`): каждая редакция — одна порция меню от диетолога, `{ from?, title, days }`; позиции несут граммовку и флаг `where: container \| packet`, шаги сборки, у каждого блюда — устойчивый `id` (слаг). Присланная редакция не переписывает прежнюю — старая неделя остаётся в файле. Первая редакция без `from` обязана описывать весь цикл; остальные обязаны иметь `from`, идти по возрастанию даты и вправе описывать подмножество дней. **Это файл Александра — он правит его руками** |
| `norms.yaml` | суточные нормы нутриентов: источник DRI (Food and Nutrition Board), группа «мужчины 19–30»; часть ключей нормы намеренно не имеет — каротиноиды, ретинол, ЭПК и ДГК, сахара, насыщенные и полиненасыщенные жиры, холестерин; шапка файла объясняет по каждому, почему |

В браузер оба попадают через `?raw`-импорты (`src/data/load.ts`) — приложение работает
офлайн, сети не требует. `loadData()` отдаёт вместе с `products`/`menu`/`norms` ещё и
`productsRevision` (текущую ревизию справочника, `parseProductsRevision`) — источник для
снапшота записи дневника и для сравнения на экране. Тот же файл читает через `node:fs`
проверка меню.

`src/state/storage.ts` (—) — единственный, кто знает про localStorage. Ключ
`STORAGE_KEY` = `eda.state.v1`, копия при потере — `BACKUP_KEY` = `eda.state.v1.backup`.
Версия формата `CURRENT_VERSION` (сейчас 5 — миграция 4→5 добавила `extras` в
`DayLog`, книгу `customFoods`, очередь `foodRequests` и `Settings.shturmanToken`;
версии 4 и старше получают пустые `extras`/`customFoods`/`foodRequests` и
`shturmanToken: ''`; версии 3 и старше вдобавок получают `cycleStartConfirmed`
как `true` — человек уже жил с датой старта, спрашивать задним числом нечестно).
Битая запись `extras`/`customFoods`/`foodRequests` выпадает целиком и считается
в `dropped`, соседние записи остаются. `deserialize`
**никогда не бросает** и отдаёт не голый `AppState`, а `LoadResult` — `{ state, source,
dropped }`, `source: StateSource` = `'stored' | 'default' | 'newer-version' | 'corrupt'`.
`'newer-version'` — хранилище держит состояние сборки НОВЕЕ этой; ключ localStorage при
этом не трогается, чтобы будущая сборка не потеряла данные, автосохранение запрещено.
`'corrupt'` — текст не разобрался как JSON вовсе; автосохранение поверх РАЗРЕШЕНО, потому
что `loadState` уже отложила дословную копию текста под `BACKUP_KEY` (`backupText`).
`dropped` — сколько записей приёмов не пережило санитизацию при этой загрузке (чужой
слот, доля вне (0, 1) у «съел часть», непоправимо битая запись); при `dropped > 0`
`loadState` тоже откладывает копию под `BACKUP_KEY`, а `source` остаётся `'stored'`.
Битый день внутри `log` выпадает только тогда, когда в нём не осталось ни одной живой
записи (`sanitizeDayLog`); битый `cycleDay` день не уносит — становится `null`
(`DayLog.cycleDay: number | null`), записи приёмов важнее подписи. Доля съеденного при
чтении хранилища выводится из статуса, а не берётся из поля (`resolveFraction`).
Отсутствующий или битый снапшот нутриента у записи даёт `UNKNOWN_POSITION`
(`known: 0, total: 1`), а не ноль позиций (`sanitizeNutrients`). `loadState` — тонкая
обёртка `deserialize` поверх `localStorage`, тоже отдаёт `LoadResult`. `saveState`
возвращает `SaveResult` — провал записи не глотается, экран
показывает причину.

## Скрипты — `scripts/`

| Файл | Что делает |
|---|---|
| `lib/usda.mjs` | единственное место знаний о CSV USDA SR Legacy: чтение `food.csv`/`food_nutrient.csv`/`food_category.csv`/`measure_unit.csv`/`food_portion.csv` (`loadFoods`, `loadCategories`, `loadMeasureUnits`, `loadPortions`, `loadNutrientsFor`), `resolveFdcDir(argvPath)` — путь к распакованной выгрузке из аргумента либо переменной окружения `FDC_DIR`, `per100Of`, `resolveSpec(spec, {foods, categories, nutrientsById})` — чистый расчёт `FoodResult`. `build-products.mjs` собран поверх него |
| `build-products.mjs` | собирает `products.yaml` из офлайн-выгрузки USDA SR Legacy; `npm run products` |
| `food-search.mjs` | `node scripts/food-search.mjs "<запрос>" [--limit 25]` — поиск строк USDA по совпадению токенов запроса в описании, вывод JSON с `fdcId`/`description`/`category`/`portions`; единственный инструмент, который headless-модель на домашнем ПК вызывает при разборе своей еды |
| `resolve-food.mjs` | stdin — спецификация `FoodSpec` (`{title, components: [{fdcId, grams, note?}]}`), stdout — `FoodResult` с `per100` каждого компонента; коды 0 (успех) / 2 (отказ данных, например неизвестный `fdcId`) / 1 (прочая ошибка) |
| `check-menu.ts` | **проверка меню до закупки поваром**; `npm run check-menu` |
| `make-icons.mjs` | иконки PWA и 12 стартовых экранов iOS из одного силуэта-миски; `npm run icons` |
| `shots.mjs` | снимки экранов headless-Chrome через DevTools-протокол без библиотек (телефонная ширина, сценарий «обед наполовину, ужин целиком», все шторки, перенос блюда между днями, своя еда во всех состояниях очереди) и проверка, что полосы покрытия не пустые; `npm run shots -- [url] [каталог]` при поднятом dev-сервере, Chrome через env `CHROME` |

**Два уровня строгости проверки меню.** Без флага (локально, гейт перед закупкой) любое
нарушение даёт `exit 1`. С `--warn-only` (в выкатке) сломанный файл меню по-прежнему
валит сборку, а не сошедшееся питание печатается предупреждением: меню на восемьдесят
калорий легче нормы — не повод оставлять человека без приложения.

Отчёт печатает каждую редакцию отдельно, своей шапкой («РЕДАКЦИЯ: имя, действует
с датой; дней: N из 8»), и делит нарушения редакции на «Так устроена вся редакция»
(правило сработало больше чем в половине её дней — замысел диетолога, не опечатка,
одна строка со счётчиком и примером) и «Выбивается из редакции — проверить»
(кандидаты в опечатку, поимённо); печатает `printViolations`.

## Что важно знать до правок

- Прямого пути из браузера в Apple Health нет и быть не может. Мост — «Команды»,
  и подтверждение приходит только возвратом `x-success` в приложение.
- Записать несколько показателей одним действием «Команд» нельзя — сколько показателей,
  столько действий. Приложение всегда отдаёт весь словарь; сколько ляжет в Health,
  решает команда, а не приложение.
- `satFat`, `monoFat`, `polyFat` в Health не попадают — таких типов образца нет.
  Они остаются в буфере обмена и в CSV.
- Ключей, токенов и паролей в репозитории нет. Разбор своей еды ходит к воркеру
  Штурмана с токеном приложения (`Settings.shturmanToken`), но токен вводит человек
  в Настройках и хранит его только localStorage браузера — в код, репозиторий и текст
  ошибок клиента (`foodClient.ts`) он не попадает.
